## 项目一句话版本

我做了一个面向长视频学习场景的 Agent 应用：把 Bilibili 视频处理成可阅读讲义、可追溯证据索引，并进一步提供页面内 Copilot 和 MCP 对外消费能力。

## 简历项目经历长版

### 项目名称

LectureMind：面向长视频学习场景的“视频讲义生成 + 证据驱动 Copilot / MCP”系统

### 项目描述

基于 FastAPI、SQLite 和多模型协作链路，构建了一个将 Bilibili 视频转为结构化讲义的 Agent 应用。系统会先采集视频元数据、字幕、关键帧和封面，再构建讲义中间表示 `LectureIR`，进一步编译为面向读者的讲义结构和面向系统的证据索引，最终以 HTML 讲义、Copilot 问答和 MCP Server 三种形式对外提供消费能力。

### 可直接用于简历的职责与亮点表述

- 设计并实现了从 Bilibili 视频到讲义生成的端到端处理链路，覆盖元数据抓取、字幕提取、关键帧抽取、结构化理解、HTML 渲染与本地持久化。
- 构建了讲义中间表示 `LectureIR`，并进一步拆分为面向阅读的 `Lecture Note IR` 与面向检索的 `Evidence Index`，支持讲义阅读、证据回溯和下游 Agent 消费。
- 针对长视频场景设计了基于时长档位的长度路由、章节规划、缓存与降级机制，避免单次大模型调用在上下文与输出长度上失控。
- 实现了基于讲义与证据索引的 Copilot 问答能力，支持 SSE 流式返回、混合检索、工具调用事件输出与回答锚点校验。
- 将讲义知识能力封装为独立 MCP Server，支持 `stdio` 与 `HTTP + SSE` 两种接入方式，便于外部 Agent 客户端复用。
- 补充了 Docker 部署、启动脚本、重渲染脚本、QA / preflight 流程与测试体系，提升系统的可部署性与可维护性。

## 面试自我介绍版

### 1 分钟版本

我做的项目叫 LectureMind，目标是把 Bilibili 上的长视频课程处理成更适合复习和继续提问的学习材料。它不是普通的视频摘要器，而是先把视频拆成字幕、关键帧、封面等原材料，再构建一个结构化的讲义中间表示 `LectureIR`。在这个基础上，系统会进一步编译出两套结构：一套是给人读的讲义结构，一套是给系统检索和追溯用的证据索引。最终产物除了 HTML 讲义，还有基于证据检索的 Copilot 和独立 MCP Server。我觉得这个项目最有价值的点，是把“生成内容”和“消费内容”打通了，而且考虑了长视频、证据回溯和工程化部署这些现实问题。

### 3 分钟版本

LectureMind 是一个面向长视频学习场景的 Agent 应用。它的输入是 Bilibili 视频链接，系统会先做元数据抓取、字幕提取、关键帧抽取和封面缓存，把视频变成一组可复用的原材料。然后在理解层里，系统不会直接生成最终 HTML，而是先构建 `LectureIR`，把章节、教学笔记、知识单元、视觉证据、复习问题这些内容结构化下来。  

接着，项目会把 `LectureIR` 编译成两种投影：一种是面向读者的 `Lecture Note IR`，强调教学单元和阅读顺序；另一种是面向系统的 `Evidence Index`，强调证据对象、关系和锚点。这样后续的 HTML 渲染、Copilot 问答和 MCP 对外服务都可以共用同一套知识底座。  

在消费层，我实现或接入了基于讲义和证据索引的 Copilot，支持 SSE 流式问答、混合检索和锚点校验；同时项目也把知识查询能力暴露成独立 MCP Server，方便外部 Agent 客户端接入。工程上，这个项目还补了配置层、SQLite 持久化、Docker、重渲染脚本、QA 和发布检查。我觉得它最像一个完整项目的地方，在于它不只是一个 prompt demo，而是有结构化中间层、有对外工具面，也有部署和验证链路。

## 最值得强调的项目亮点

### 1. 不是“视频摘要器”，而是“讲义知识编译系统”

这句话非常关键。  
如果你一上来只说“做了视频总结”，面试官很容易把它理解成一个套壳应用。  
但如果你说：

> 我把视频先编译成中间表示，再拆成讲义结构和证据结构，最后支持 Copilot 和 MCP 消费。

项目层次会立刻上去。

### 2. 双投影设计

这是最能体现系统设计能力的地方。

- `Lecture Note IR` 面向读者；
- `Evidence Index` 面向系统。

这个点很适合当作项目的“架构主卖点”。

### 3. 长视频处理不是单 prompt

你可以强调：

- 需要按时长做路由；
- 需要章节规划；
- 需要 cache、critic、reviser 等策略；
- 需要处理上下文和输出长度限制。

### 4. 有完整消费层

项目不是“生成完报告就结束”，而是继续支持：

- 页面内 Copilot；
- RAG 检索；
- MCP 对外服务。

### 5. 有工程化闭环

这部分决定项目像不像真实系统：

- 配置管理；
- SQLite 持久化；
- Docker 与启动脚本；
- QA 与测试；
- 发布前检查。

## 常见面试追问与回答提纲

### 问题 1：这个项目和普通视频总结工具最大的区别是什么

建议答法：

- 普通工具的重点是把长内容压缩成短文本。
- 这个项目的重点是把视频编译成一个可阅读、可检索、可追溯、可继续问答的知识结构。
- 所以它不仅生成讲义，还生成证据索引，并把这些能力继续暴露给 Copilot 和 MCP。

### 问题 2：为什么要设计 `LectureIR`

建议答法：

- 因为 HTML 只是展示层，不适合作为事实源。
- 先有结构化中间表示，后续才能做校验、重渲染、检索和多消费端复用。
- `LectureIR` 让系统不依赖单一展示形式。

### 问题 3：为什么要把讲义和证据分开建模

建议答法：

- 面向读者的结构追求的是好读、顺畅、有教学组织。
- 面向系统的结构追求的是细粒度、可索引、可回溯。
- 两种目标天然不同，所以拆成双投影更合理。

### 问题 4：长视频为什么难做

建议答法：

- 原始材料更长；
- 单次生成更容易超过模型输出上限；
- 内容密度更高；
- 更需要章节规划和分段处理。

然后再补一句：

> 所以项目里做了基于时长的 profile 路由和章节规划，而不是所有视频都走一套 prompt。

### 问题 5：Copilot 为什么不直接读 HTML

建议答法：

- HTML 是展示结果，不是结构化事实源。
- 直接读 HTML 粒度不稳定，也不利于证据回溯。
- 所以项目让 Copilot 直接消费讲义结构和证据索引。

### 问题 6：为什么要做 MCP

建议答法：

- 因为项目产出的核心不是页面，而是一套可复用的讲义知识能力。
- MCP 把这些能力封装成外部 Agent 可调用的工具面，让项目从单一应用升级为知识服务后端。

### 问题 7：项目里最有挑战的部分是什么

你可以优先选下面三个角度中的一个：

- 长视频结构化抽取与长度路由；
- 双投影数据建模；
- 证据锚点校验与检索式 Copilot。

这三个角度都比“调模型 API”更能体现技术深度。

## 讲项目时最好避免的表达

- 避免说“我做了一个视频总结网站”。
- 避免只强调用了哪些模型，而不解释系统结构。
- 避免把所有设计文档里的未来规划都说成已落地事实。
- 避免声称“生产级高并发”之类没有明确证据支持的话。
- 避免泛泛说“用了多智能体”，却说不清具体在哪一层、解决了什么问题。

## 建议的表达主线

如果你要对外统一表达这个项目，最稳的一条主线是：

1. 这是一个面向长视频学习场景的 Agent 应用。
2. 它先把视频采集成结构化原材料。
3. 再构建 `LectureIR`，并拆成讲义与证据双投影。
4. 最终通过 HTML、Copilot 和 MCP 三种方式对外消费。
5. 工程上补齐了缓存、部署、测试和 QA，做成了一个可运行系统。
