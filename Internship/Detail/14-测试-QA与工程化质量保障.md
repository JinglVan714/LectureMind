单视频真机端到端验证。`@d:\Diet_Agent_NEW\scripts\` 下。

调用方式：


## 自动化 QA：qa_full.ps1 + preflight.ps1

### qa_full.ps1（3 步回归）

`@d:\Diet_Agent_NEW\scripts\qa_full.ps1`：

```powershell
# 1. Front-end syntax — node --check app/static/copilot.js
# 2. Python bytecode sanity — python -m compileall app tests scripts
# 3. Full pytest sweep — python -m pytest tests/ -v
```

任何一步失败就 exit 非零。可通过 `-CondaEnv` / `-NoConda` 切换 Python 来源。

### preflight.ps1（发布前一键检查）

`@d:\Diet_Agent_NEW\scripts\preflight.ps1` 是 GitHub 上传前的「最后一道关」。它检查：

1. `.gitignore` 覆盖 `.env / data/ / .tmp/ / .tmp_pytest/ / .tmp_smoke/ / tmp/`。
2. `.dockerignore` 覆盖 `.env / data/ / tests/ / docs/`。
3. `.env` 不被 git 跟踪（`git ls-files --error-unmatch .env` 应非 0）。
4. `data/` 不被 git 跟踪。
5. `.env` 中的 DEEPSEEK / DASHSCOPE / BASIC_AUTH 三个 key 不是 placeholder。
6. `.env.example` 中**真的**只有 placeholder（用正则识别非 placeholder 的 `sk-` 开头串）。
7. 默认还会 spawn `qa_full.ps1` 跑完整回归（`-SkipTests` 可绕过）。

输出 `[ok] / [warn] / [err]`。有 err 时 exit 1，warn 不阻止。

### 设计动机

`.env` 误推到 GitHub 会立即泄露所有 API key。preflight 的存在让「忘了 git rm --cached .env」这种事故有自动化兜底。它把「发布前还要记得检查这些」变成「跑一个脚本就行」。

## 工程化分层

整套质量保障在「时间维度」上分四层：

```
开发时                                  → unit / integration tests (pytest)
PR 时（CI 还没接，但可以自动化）         → qa_full.ps1
发布前                                 → preflight.ps1（含 qa_full）
正式发布前最后一步                      → release_checklist.md（人工 + 真机）
运行时                                 → /healthz + pipeline.last_run_timing
```

测试与脚本之间不重复——`qa_full` 跑 unit；`preflight` 跑 `qa_full` + 安全检查；`release_checklist` 跑 `preflight` + 真机 + 人工 UI 抽查。

## Telemetry → 验证脚本的闭环

整套质量保障的核心闭环：

```
Pipeline._run_inner
  └→ last_run_timing (~20 字段)
  └→ last_run_stats
  └→ _dump_ir → data/debug/<BV>.lecture_ir.json
     ↓
scripts/_verify_lecture_v2_real_e2e.py
  └→ 跑 Pipeline.run + 比对预期
  └→ 写 data/debug/<BV>.timing.json + quality_metrics
     ↓
scripts/_summarize_lecture_matrix.py
  └→ 聚合多 BV → data/debug/lecture_matrix_*.{json,md}
     ↓
docs/release_checklist.md
  └→ 人工对照矩阵报告决定是否发布
```

Telemetry 不是「调试时输出」而是「质量门禁的输入」。这种「让 telemetry 直接驱动质量决策」的工程模式比起「靠日志肉眼判断」可量化得多。

## 面试可展开点

### 1. 为什么不上 CI（GitHub Actions）

CI 当然有用，但短期内项目是「内部工具 + 自托管」形态，发布频率低。手动跑 `qa_full.ps1 / preflight.ps1` 已经够；CI 的边际价值要等到协作者多了 / 发布频次高了才显现。**release_checklist.md** 第 5 章已经留了 CI 入口（`.github/workflows/ci.yml`）只是没急着启用。

### 2. 单测和真机测试为什么各搞一套

单测用 mock，跑得快（秒级），覆盖 logic；真机用真模型，跑得慢（分钟级），覆盖 prompt 质量、模型稳定性、真实数据形态。两者目标不重叠。**`qa_full` 只跑单测，真机回归用 `_verify_*` 手动触发**——这是「快慢分离」的标准做法。

### 3. 为什么把 telemetry 写成可量化 JSON 而不是日志

日志看一次扔一次，下次还要肉眼对比。JSON 让 `_summarize_lecture_matrix` 能跨视频聚合「chapter budget 失败的视频列表」「平均 token 节省百分比」「最慢 stage」。当系统跑过 10+ 个真实 BV，肉眼对比根本看不过来；矩阵报告能立刻指出问题。

### 4. 为什么 preflight 要单独检查 .env 是否被 git tracked

PowerShell `git rm --cached .env` 的语义比直观要微妙——如果以前 git add 过，删 `.env` 文件后 git 仍认为它存在。preflight 用 `git ls-files --error-unmatch .env` 主动探测这种「历史已添加但忘了 untrack」的状态，是「真正的工程防御」。

### 5. release_checklist 为什么不写脚本自动跑

部分项目可以（已经在 `preflight.ps1` 里），但有些不行：

- 「手动 QA 抽查」需要人去看 UI。
- 「LICENSE 内容由用户决定」需要人手填。
- 「Actions 第一次绿灯」需要在 GitHub 网页上确认。

这些步骤本质上需要人工 judgment。把可自动化的塞进 preflight，无法自动化的留在 checklist——分清「能自动的」和「必须人审的」是工程交付的成熟标志。
