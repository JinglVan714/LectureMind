# 长度路由与章节规划

## 文档定位

这一篇集中讲长视频生成里最关键的「不是一套 prompt 打天下」的实现。覆盖四个模块：

- `app/understand/profile.py` — 按时长选择策略组合（tiny / standard / long / epic）。
- `app/understand/length_adapt.py` — 把策略组合具象化为「章节数 / 关键帧 / 知识单元」等数值预算。
- `app/understand/chapter_planner.py` — 确定性的章节锚点抽取。
- `app/understand/chapter_cache.py` — 章节级 prompt 缓存，把重跑成本拍到「只重做全局 pass」。

主链路在 `@d:\Diet_Agent_NEW\app\pipeline.py:171-225` 调用这四个模块。

## 一句话定位

「长度路由」是一组**确定性**前置决策：先看时长选档位 → 再算预算 → 再切章节锚点 → 再决定哪些昂贵步骤启用缓存。整套机制完全发生在 LLM 调用之前，**让一次大模型调用消耗的资源跟视频时长可预测地挂钩**。

### LectureProfile dataclass

```python
@dataclass(frozen=True)
class LectureProfile:
    name: ProfileName
    duration_sec: float
    use_chapter_planner: bool
    use_map_reduce: bool
    use_chapter_cache: bool
    critic_mode: CriticMode          # "off" / "full" / "projected"
    reviser_mode: ReviserMode        # "off" / "patch" / "full"
    study_question_mode: StudyQuestionMode
    chapter_planner_mode: ChapterPlannerMode

    def with_duration(self, duration_sec) -> "LectureProfile":
        return replace(self, duration_sec=float(duration_sec))
```

`frozen=True` + 模板表 + `with_duration` 是「不可变模板 + 一次性具体化」的标准做法。下游所有阶段读这一份 profile，**不会**因为状态被某个模块改了导致其他模块行为漂移。

## LengthBudget：把档位翻译成数字预算

`@d:\Diet_Agent_NEW\app\understand\length_adapt.py:136-181` 把时长翻成一组**所有 prompt 都能读**的整型预算：

```python
@dataclass(frozen=True)
class LengthBudget:
    duration_sec: float
    chapters_min: int          # 章节下界
    chapters_max: int          # 章节上界
    mainline_max: int          # 全局 mainline 项数上界
    global_visual_limit: int   # 全局视觉证据上界
    glossary_max: int          # 术语上界
    review_questions_max: int  # 复习题上界
    keyframe_min: int          # 关键帧下界（已经过 length-adapt 放大）
    keyframe_max: int          # 关键帧上界
    study_questions_min: int
    study_questions_max: int
```

### 关键曲线

`@d:\Diet_Agent_NEW\app\understand\length_adapt.py:40-133` 几个函数定义曲线：

- `chapters_target(duration)` — 分段函数：`<10min → 3-4` / `10-30 → 4-6` / `30-60 → 6-9` / `60-90 → 7-11` / `90+ → 8-12`。
- `mainline_max` — 线性 `4 + m/7.5`，钳到 `[4, 14]`。
- `keyframe_window(duration, base_min, base_max)` — 把 `KEYFRAME_MIN/MAX` 作为下界，按 `m*1.5+4`（max）和 `m*0.4`（min）放大。
- `global_visual_limit` — `<=10min → 5`，超过则 `5 + (m-10)/3.5`，上限 24。
- `study_questions_target` — `<10 → 4-6` / `<30 → 5-8` / `<60 → 6-10` / 其他 `7-12`。

每条曲线都有「线性 + 上下界」结构。设计文档里强调了三个目标：

- 短视频依然紧凑，不破坏已有的 HTML 快照。
- 长视频每分钟密度保持稳定，30 分钟和 5 分钟应该看起来「同样饱满」。
- 病态输入（多小时直播）不会爆 prompt / 页面。

### density_hint

`@d:\Diet_Agent_NEW\app\understand\length_adapt.py:183-192` 还输出一段可以直接拼到 prompt 里的中文 hint，例如「较长视频（30-60 分钟），需要更密的章节与知识单元，通常每 5-8 分钟应有独立章节支持。」这是把「策略意图」直接喂给 LLM 的常用模式。

## ChapterPlanner：三信号融合 + 两种模式

`@d:\Diet_Agent_NEW\app\understand\chapter_planner.py:1-32` 写明了设计意图——**确定性章节锚点抽取**，不调任何 LLM，可以单元测试，零 I/O。

### 三种候选信号

`@d:\Diet_Agent_NEW\app\understand\chapter_planner.py:226-302`：

- **转折短语**（最强信号）：
  - 正则匹配字幕段落开头，例如「那么我们来看」「接下来我们进入」「第三部分」「总结」「首先，」等。
  - 默认置信度由 `LECTURE_PLANNER_TRANSITION_PHRASE_CONFIDENCE` 控制。
  - 注释强调正则**故意保守**，避免「那么」一个字就触发。
- **静音间隔**：
  - 相邻字幕 segment 之间空白 ≥ `LECTURE_PLANNER_SILENCE_SEC` 时触发。
  - 适合处理「讲师停顿几秒切下一页」的场景。
- **视觉类型跳变**：
  - 相邻关键帧的 `visual_type` 变了（`slide_text → code` / `person → diagram` 等）。
  - 必须在 `±2 秒` 内能找到字幕段落边界，才认作真正的章节切换。

### 候选合并

`@d:\Diet_Agent_NEW\app\understand\chapter_planner.py:180-186`：

```python
candidates = _collect_candidates(segments, frames, settings)
candidates = _snap_to_segment_boundaries(candidates, segments)
candidates = _dedupe_candidates(candidates)
```

`_snap_to_segment_boundaries` 把候选时间贴到最近的字幕 segment 起点，让最终锚点对齐到「人能讲到那里」的时间。`_dedupe_candidates` 合并几乎相同时间点的候选，保留最高 confidence 的来源。

### hint vs structural 两种模式

`@d:\Diet_Agent_NEW\app\understand\chapter_planner.py:187-218`：

- **hint** —— tiny / standard 用。把 top `chapters_max + 2` 个候选当**建议**喂给 LLM，最终边界由 LLM 决定，允许少于 `chapters_min`。
- **structural** —— long / epic 用。强约束 `chapters_min ≤ N ≤ chapters_max`，缺则用等分切（`equal_split`），多则贪心合并最低置信度的相邻章节。

### M2.2 章节宽度兜底

`@d:\Diet_Agent_NEW\app\understand\chapter_planner.py:204-217` 后置加了一层「任意章节宽度 > `LECTURE_CHAPTER_MAX_DURATION_SEC` 时按 `ceil(width / threshold)` 等分切」。切出来的子章节 source 标 `equal_split_overflow`，让 telemetry 能识别出哪些章节是事后兜底来的（往往对应「锚点信号弱」的区域）。

### 输出形态

```python
@dataclass(frozen=True)
class ChapterAnchor:
    start_sec: float
    end_sec: float
    confidence: float           # [0, 1]
    anchor_text: str            # 截断到 ~80 字符的字幕摘录
    source: AnchorSource        # transition_phrase / silence / visual_shift / equal_split / equal_split_overflow
    mode: AnchorMode            # hint / structural
```

锚点是**连续的、半开区间**：第 i 章的 `end_sec == 第 i+1 章的 start_sec`，第一章必从 0.0 开始，最后一章必到 `duration_sec`。

## ChapterCache：长视频 Map-Reduce 的缓存底座

### 为什么需要单独缓存

`@d:\Diet_Agent_NEW\app\understand\chapter_cache.py:1-29` 的 module docstring 解释得很清楚：

- 长 / epic 视频走 `MapReduceIRBuilder`，每章一次 LLM 调用。一个 60 分钟视频 8 章 → 8 次调用；epic 视频 12+ 章。
- 第二次跑同一个 BV（或两个 BV 恰好有完全相同的 chapter prompt）时，如果没有缓存，每次都付完整时延。
- 章节级缓存把「时延摊到第一次」。

### 缓存键：`compute_prompt_hash`

`@d:\Diet_Agent_NEW\app\understand\chapter_cache.py:87-126` 定义了哈希函数：

```python
payload = {
    "v": prompt_version,
    "model": model_id,
    "start": round(chapter_start_sec, 3),
    "end": round(chapter_end_sec, 3),
    "segments": [{"ts": round(s.start, 3), "text": s.text.strip()} for s in segments],
    "frames": [{"ts": round(f.ts, 3), "ocr": f.ocr_text.strip(), "caption": f.caption.strip()} for f in frames],
}
canonical = json.dumps(payload, sort_keys=True, ensure_ascii=False, separators=(",", ":"))
return hashlib.sha256(canonical.encode()).hexdigest()
```

几个关键设计：

- 时间戳一律 `round(ts, 3)`（毫秒精度），与 `KeyframeExtractor` 里的 ms 量化精确对齐。这条对齐线 commit `09df83f` 中专门修复过——上游量化 + 下游量化必须一致，否则 100% miss。
- payload 是**规范化 JSON**（sort_keys + 无空格），保证 Python dict 顺序变了不影响哈希。
- key 里包含 `model_id` 和 `prompt_version`，**任何 prompt 改版都应同步 bump `LECTURE_MAP_PROMPT_VERSION` 来一次性废掉旧缓存**。

### 表结构

`@d:\Diet_Agent_NEW\app\understand\chapter_cache.py:142-164`：

```sql
CREATE TABLE chapter_cache (
    prompt_hash    TEXT PRIMARY KEY,
    chapter_json   TEXT NOT NULL,
    model_id       TEXT NOT NULL,
    prompt_version TEXT NOT NULL,
    bv_id          TEXT NOT NULL,
    chapter_index  INTEGER NOT NULL,
    chapter_start  REAL NOT NULL,
    chapter_end    REAL NOT NULL,
    created_at     REAL NOT NULL,
    accessed_at    REAL NOT NULL,
    hit_count      INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_chapter_cache_bv ON chapter_cache(bv_id);
CREATE INDEX idx_chapter_cache_model_version ON chapter_cache(model_id, prompt_version);
```

`bv_id` 索引让 `clear_by_bv_id(bv_id)` 在 `--force` 重跑时只清掉一个视频的缓存而不污染其他视频。

### get / put / stats

`@d:\Diet_Agent_NEW\app\understand\chapter_cache.py:205-273` 的 API 非常对称：

- `get(prompt_hash)` — 命中时同时 bump `hit_count` 和 `accessed_at`，给未来 LRU 清理留口子。
- `put(prompt_hash, chapter_payload, model_id, prompt_version, bv_id, chapter_index, chapter_start, chapter_end)` — `INSERT OR REPLACE`，让并发写最后写者胜。
- `stats()` — 返回 `{hits, misses, writes, rows_total}`。前三个是「本进程计数」，`rows_total` 是 SQL 实时查询。

并发安全：每次调用新开 connection，WAL 模式 + 30s timeout。`_counter_lock` 保护 in-process 计数器。

## 写简历可以怎么提炼

- 设计了基于时长的策略路由层（tiny / standard / long / epic），把 ChapterPlanner / Map-Reduce / Critic / Reviser / StudyQuestion 等模块的启用与模式统一收敛到一份 `LectureProfile`，避免在多个 prompt / 模块里重复判断「这是不是长视频」。
- 实现了确定性的 `ChapterPlanner`，融合转折短语 / 静音 / 视觉跳变三种本地信号，并在 hint / structural 两种模式下分别走「向 LLM 提示」与「强结构约束 + 等分兜底」两种策略。
- 引入了基于 SHA-256 (model × prompt_version × 规范化 chapter 输入) 的 `ChapterCache`，让长视频 Map-Reduce 链路从「每跑必付全单」变成「首跑后接近免费」，并通过 telemetry（hits / misses / writes / rows_total）让缓存命中率可量化。
- 修复了关键帧时间戳精度漂移导致的缓存 100% miss 问题，把上游 keyframe extractor 与下游 prompt hash 的时间值统一到毫秒量化。

## 面试可展开点

### 1. 为什么 standard 上界要从 25 分钟降到 15 分钟

实际跑 23 分钟代码密集视频时单次 IR JSON 超过 DeepSeek 8192-token 输出上限，触发 `finish_reason=length` 截断。把阈值降到 15 分钟相当于「让任何会超 token 的视频都直接走 Map-Reduce」，避免「先单次跑失败再 fallback」的浪费。

### 2. 为什么 ChapterPlanner 完全不调 LLM

两个原因：可测试 + 可缓存。如果 chapter 切分本身要花一次 LLM 调用，测试要打 mock、性能预算要重新算、缓存要重新设计。纯确定性规则可以单元测试到 100% 覆盖，给下游 LLM 当 hint 足够。

### 3. 为什么 ChapterPlanner 不直接定 chapter，而是分 hint / structural

短视频信号本来就少，强制要 6 章会出现凑数章节；长视频信号充裕，但 LLM 可能合并相近章节导致密度不足。区分两种模式让短视频信赖 LLM 判断，长视频强约束结构。

### 4. 为什么 ChapterCache 要把 model / prompt_version 进 hash

模型升级或 prompt 模板改动后，旧缓存的语义就变了。把这两项放进 key 让缓存「自动作废」——不用人手清库。

### 5. 为什么时间戳要量化到毫秒

PySceneDetect 给的是微秒精度浮点，但实际抽帧是按 ms 取的。如果 hash 里保留微秒，fresh 路径与 cached 路径会算出不同 hash，缓存全 miss。这是「上游不一致 → 下游失效」的典型，修在上游 1 行代码比下游每处都加 normalize 干净得多。

## 当前文档中的事实与推断

### 事实

- profile 表是冻结 4 档，阈值默认 `(180, 900, 3600)` 秒。
- `LengthBudget` 把策略翻译成 11 个整数字段。
- ChapterPlanner 三信号 + 两模式，最终输出 `ChapterAnchor[]`。
- ChapterCache 是独立 SQLite 文件，key 包含 model + prompt_version + 规范化 chapter 输入。
- 在 pipeline 里失败均降级为空 / None，主链路不中断。

### 推断

- 把这套「档位 + 预算 + 锚点 + 缓存」做成 4 个独立模块而不是合并到 IR builder 内部，是为了让长视频每一道工序都能独立单元测试和回归。
