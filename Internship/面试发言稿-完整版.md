# LectureMind 项目面试发言稿

---

## 开场（30 秒）：一句话说清楚这个项目

> "我做了一个叫 LectureMind 的项目——**把 B 站技术类视频自动转成结构化的图文讲义，并且支持对着讲义提问、系统能引用视频原文回答。** 从贴链接到生成可问答的讲义，全程自动化。"

---

## 第一部分：为什么要做这个（1 分钟）

**痛点：**

> "B 站上有很多优质的技术课程——机器学习、Rust 教程、算法讲解。但看视频学习有几个问题：
>
> - **复习效率低**：想回顾某个知识点，得拖着进度条找，2 小时的视频找 30 秒的内容。
> - **没有结构化**：视频是线性的，但知识是网状的——你很难一眼看出「这个概念依赖哪几个前置概念」。
> - **不能搜索**：Ctrl+F 对视频无效。
>
> 所以我想做一个工具，把视频「压」成讲义——保留原视频的关键帧和字幕引用，同时让知识结构化、可搜索、可问答。"

**一句话总结价值：**

> "把被动看视频，变成主动读讲义 + 提问。"

---

## 第二部分：整体架构（2 分钟）——用餐厅类比

> "整个系统我把它设计成一条流水线，可以类比成一个餐厅厨房："

```
贴 B 站链接
    ↓
【备菜间 - Ingest 层】把视频拆成原材料（字幕、关键帧、封面）
    ↓
【配菜员 - VLM 层】给每张截图配文字描述
    ↓
【主厨 - IR 构建层】LLM 把原材料「炒」成结构化讲义（LectureIR）
    ↓
【菜谱 - LectureIR Schema】定义讲义的数据结构——所有下游消费的唯一事实源
    ↓
【摆盘 - 双投影编译】同一份菜，摆成两种盘：给人看的 + 给机器检索的
    ↓
【服务员 - Copilot】用户对着讲义提问，系统找证据回答
```

> "技术栈：Python + FastAPI + SQLite + LangGraph + DashScope（通义千问 VL + DeepSeek）。全部本地可跑，一个 Docker 镜像搞定。"

---

## 第三部分：逐层展开（5-6 分钟）——挑重点讲

### 第 1 层：Ingest — 视频原料采集

> "第一层做的事很简单——给一个 B 站链接，交出三样东西：**字幕、关键帧截图、封面**。
>
> 但有一个工程细节值得讲——**字幕的三级降级策略**：
>
> - 优先用 UP 主自己上传的 CC 字幕（最准）
> - 没有就用之前跑过的 Whisper AI 听写缓存
> - 缓存也没有就当场跑 Whisper 听写（最慢但兜底）
>
> 为什么这么设计？因为技术类长视频 UP 主经常不传字幕，但这些视频恰恰是最值得做讲义的。如果「没字幕就报错」，能处理的视频范围会缩得很小。
>
> 另外，字幕、关键帧、封面三件事**互不依赖**，我用 `asyncio.gather` 并行跑——串行要 5 分钟，并行只要最慢的那个任务的时间。"

---

### 第 2 层：VLM — 视觉理解 + 分级

> "关键帧抽出来之后，需要让视觉模型「看图说话」——描述每张截图里有什么。
>
> **核心问题：每张都详细描述太贵了。** 一个 44 分钟的视频约 50-60 帧，每帧详细描述要 ~1000 token。但大部分帧不需要这么贵——连续重复的幻灯片、黑屏过场、UP 主的大脸，给个简短描述就行。
>
> 所以我设计了**两级 prompt**：
> - HIGH：完整描述（caption + OCR + 画面类型 + 评分），~1000 token
> - LOW：只提取 OCR 文字，~200 token
>
> **关键设计：在调模型之前就判断该走哪档。** 我用三个纯 CPU 信号——dHash 相似度（和上一张像不像）、灰度熵（画面有多乱）、边缘密度（文字边缘多不多）——在本地做分级，不花一分钱 token。
>
> 效果：token 成本下降约 40%。"

---

### 第 3 层：长度路由 + 章节规划

> "不同长度的视频不能用同一套方法处理。3 分钟的健身短视频和 2 小时的机器学习课，处理策略应该完全不同。
>
> 我设计了一套**四档策略路由**：
> - < 3 分钟 → tiny：LLM 一次性读完，不审查
> - 3-15 分钟 → standard：一次性 + Critic 审查 + Reviser 修补
> - 15-60 分钟 → long：Map-Reduce 分段处理 + 精简审查
> - 60+ 分钟 → epic：同上，但章节更多
>
> **章节规划器（ChapterPlanner）完全不调 LLM**——用三个土办法判断「这里该不该切一章」：字幕里的转折短语（「接下来我们看」「第三部分」）、讲师沉默超过 6 秒、画面类型突变（幻灯片→代码）。纯规则，可单元测试，零 I/O。
>
> 一个踩过的坑：standard 的上限原本是 25 分钟，但实际跑一个 23 分钟的代码密集视频时，LLM 输出超过了 8192 token 上限被截断。我把阈值降到 15 分钟——让任何可能超 token 的视频一开始就走分段处理。"

---

### 第 4 层：多 Agent 协作 — 提问 → 初稿 → 审查 → 修补

> "讲义不是一次 LLM 调用直出的，而是四个 Agent 接力：
>
> 1. **StudyQuestionAgent**：先让一个轻量 Agent 生成 5-10 个问题（「梯度下降的数学推导分几步？」），再把这些作为 prompt 约束喂给 IR Builder——强制它回答这些问题，而不是套「介绍背景→讲解核心→总结」的万能模板。
>
> 2. **IR Builder**：基于问题引导，生成初稿 LectureIR。
>
> 3. **Critic（审查员）**：对照原始字幕和关键帧，找出初稿的问题——「第 3 章第 2 个论点的引用在字幕里找不到」「第 5 章的代码块缺少解释」。**只找问题，不动手修**——职责分离让 Critic 的回答更短更稳定。
>
> 4. **Reviser（修补员）**：针对 Critic 发现的问题打补丁。**关键设计：Reviser 只能改 5 类字段**（quote、text、explanation、列表替换、列表追加），章节时间戳、视频画像这些禁区不在白名单里，LLM 就算提议也会被自动拒收。
>
> 补丁应用还有一个**整批回滚**机制——LLM 给的多个补丁是一个连贯的修复计划，要么全过 Pydantic 校验上线，要么一字不动。保证 Reviser 只能让 IR 变好，不能让 IR 变非法。"

---

### 第 5 层：LectureIR — 整个项目的「唯一事实源」

> "前面讲了 Agent 怎么协作生成讲义。但这里有一个关键问题——**LLM 的输出不可靠**。它可能编造时间戳、漏掉字段、把代码塞错位置。不能直接把 LLM 的输出当最终结果用。
>
> 所以 LectureIR 做了两件事：
>
> **第一，定义严格的数据结构。** 一份完整的 LectureIR 包含这些字段：
> - `core_question`：这个视频回答的核心问题，一句话
> - `mainline`：全局知识主线，3-8 条
> - `chapters`：每个章节的完整内容（标题、论点、代码块、公式块、关键帧）
> - `knowledge_units`：跨章节的知识单元，带 `depends_on` / `prerequisites` 显式依赖关系
> - `visual_evidence`：全局视觉证据池，每张图带重要性评分
> - `completeness`：自评——缺了什么、读者不看视频能看懂吗
> - `render_plan`：哪些区块需要在 HTML 里渲染
>
> **代码和公式是「一等公民」**——不是嵌在字符串里的文本，而是独立的结构化对象，有自己的 `language`、`code`、`explanation` 字段。这样 HTML 渲染时可以单独走语法高亮，RAG 检索时不会被切成碎片。
>
> **第二，9 步清洗 LLM 的脏数据。** `hydrate_lecture_ir_data` 函数做了一整套后处理：
> - LLM 把时间戳写成 `ts=0`（明明在视频后半段）→ 用 quote 文本在字幕里反查真实位置
> - LLM 忘了把关键帧分配到章节 → 按时间戳自动分配
> - LLM 把 mainline 写成章节标题的复制粘贴 → 清空，用 fallback 重建
> - LLM 输出「1. 梯度下降」「2、反向传播」这种序号污染 → 剥掉序号前缀
> - LLM 输出「介绍背景」「讲解核心知识」这种通用废话 → 剔除
>
> **核心思想：LLM 给什么就用什么，缺了就启发式补，错位了就纠正。** 保证最终交给 Pydantic 校验的数据永远能通过。
>
> 还有一个细节——LLM 生成的每个论点都带一个 `quote`（声称是视频原话），但 LLM 经常 paraphrase 甚至编造。我用「精确子串匹配 + 4-gram 模糊匹配」双层校验来验证 quote 是否真的在字幕里。匹配不上的 point 自动加 ⚠️ 标记——用户一眼就能看出这句话的原文锚定不可信。"

---

### 第 6 层：Map-Reduce — 长视频分段处理

> "15 分钟以上的视频走 Map-Reduce：
>
> - **Map 阶段**：按章节切成小块，每章一次 LLM 调用，只生成这一章的内容
> - **Reduce-Local**：纯 Python 把各章结果拼起来（毫秒级）
> - **Reduce-Global**：一次轻量 LLM 调用，补全局内容（主线、总结、术语表）
>
> **缓存是这一层的核心收益**。每章的 prompt 是固定的（同样的字幕、同样的帧、同样的时间边界），所以可以缓存。缓存键是 `SHA-256(模型名 + prompt版本 + 规范化输入)`。
>
> 首跑：8 次 map + 1 次 global ≈ 110 秒。二跑（什么都没变）：0 次 map + 1 次 global ≈ 30 秒。80% 的 LLM 调用被缓存吃掉。
>
> **单章失败不阻断**——塞一个占位符，不写缓存（下次还能重试），其他章节正常处理。但全局 pass 失败直接抛——因为缺了 mainline 和 final_synthesis 的讲义质量不可控。"

---

### 第 7 层：双投影编译

> "这是整个项目架构上最值得讲的设计。
>
> LectureIR 生成之后，不是直接渲染 HTML。而是**同时编译成两份产物**：
>
> - **LectureNoteIR（给人看）**：按教学逻辑组织——每章分配一个角色（主张型、流程型、边界型），按角色选模板，段落分组，视觉槽位
> - **EvidenceIndex（给机器用）**：5 类证据对象（章节、引用、帧、流程、概念）+ 证据间关系（谁支撑谁）+ 三套锚点（视频秒数、页面位置、证据 ID）
>
> 为什么分两份？因为渲染 HTML 需要的信息和 RAG 检索需要的信息完全不同。分开让每份结构各司其职，互不污染。
>
> 三套锚点让不同消费方各取所需：读者点 `[t=02:00]` 跳视频位置，Copilot 回答时引用「讲义第 3 章」，RAG 命中后反查证据 ID。"

---

### 第 8 层：Copilot — 混合检索 + ReAct Agent

> "用户对着讲义提问，系统要找到相关片段并组织答案。
>
> **混合检索**：向量搜索（语义相似度）+ 全文搜索（关键词匹配），两路结果用 RRF 融合。因为用户查询很多样——「损失函数怎么算」是自然语言（向量擅长），「QKV 的 softmax」是术语片段（BM25 擅长），只用一种会漏。
>
> **Chunk 设计**：按讲义语义结构切（教学笔记、引用、代码块、公式块、关键帧 OCR），不按字数切。每个 chunk 是一个语义完整单元，命中后不需要拼上下文。
>
> **ReAct Agent**：LangGraph 单节点循环——模型决定调哪个工具 → 工具返回结果 → 模型再决定下一步。整个流程 note-first / evidence-second：先搜讲义主线，再找证据下钻。
>
> **SSE 流式推送**：前端能看到每一步——正在调什么工具、找到了什么、答案逐字生成。
>
> **锚点校验**：模型生成的答案里会带 `[t=12:30]`、`[F7]` 这类引用。我用确定性 Python 函数逐条检查这些引用是否合法——时间戳是否在视频范围内、帧 ID 是否真实存在。非法的替换或剥掉。**凡是能确定性算的，就不交给模型。**
>
> **三层降级**：sqlite-vec 扩展加载失败 → FTS-only；向量搜索网络挂了 → 只用 FTS；整批 embed 失败 → 不写库，讲义照样能看。RAG 是锦上添花，不是没你不行。"

## 第四部分：工程化亮点总结（1 分钟）

> "回顾整个项目，有几个我比较得意的工程决策：

> 1. **分层容错**：核心路径（采集、生成、渲染）fail-fast，增强路径（缓存、审查、修补、检索）降级继续。单个 LLM 调用挂了不影响整条链路。
>
> 2. **缓存无处不在**：VLM 缓存（按图片 hash 跨视频复用）、章节缓存（Map-Reduce 二跑几乎免费）、RAG 索引缓存。每一层能缓存的都缓存了。
>
> 3. **LLM 输出不可信，但也不抛弃**：hydrate 9 步清洗 + ir_sanity 4 类净化 + 锚点校验 + 白名单补丁——层层设防，把 LLM 的脏数据修成可信数据。
>
> 4. **可观测性**：每一步都记 telemetry，20+ 个字段覆盖所有阶段耗时和子统计。验证脚本直接读，不用解析日志。
>
> 5. **单 SQLite 交付**：向量检索（sqlite-vec）+ 全文检索（FTS5）+ 业务数据全在一个文件里。一份 `data/app.db` 备份就能搬走所有数据，运维成本极低。"

## 第五部分：面试官可能会追问的问题（附回答）

### Q1：为什么不用 LangChain 全套，而是自己写了很多？

> "LangChain 的抽象层太厚，调试困难。我用了 LangGraph 做 Agent 编排（它的 `astream_events` 对 SSE 友好），但 prompt 模板、缓存、数据校验都是自己写的——因为这些是业务逻辑，放在框架黑盒里反而不灵活。"

### Q2：VLM 分级为什么用 CPU 信号而不是让模型自己判断？

> "让模型判断「这张图值不值得详细描述」需要先把图送进去，省不了一次 input token。CPU 端用 dHash / entropy / edge density 几乎免费，能在调模型之前就剔掉重复幻灯片和黑屏帧。这是典型的「便宜的过滤先做」。"

### Q3：为什么缓存键里要包含模型名和 prompt 版本？

> "模型升级后返回的描述风格会变，prompt 模板改了语义也会变。把这两项放进 key 让缓存自动作废——不用人手清库。这是缓存系统的基本原则：key 必须覆盖所有会影响输出的变量。"

### Q4：Reviser 为什么做白名单而不是让 LLM 自由改？

> "Reviser 修补只想动一小块（quote / explanation / 单个 chapter 的 code_blocks）。如果允许任意 path，LLM 会偶尔顺手改 chapter timing / profile / taxonomy，导致下游静默回归。白名单把语义边界固化在代码里——LLM 提议什么不重要，能落地的只有白名单内。"

### Q5：这个项目最大的技术挑战是什么？

> "长视频的 LLM 上下文窗口管理。60 分钟视频字幕 5 万字，直接塞会爆。我的解法是三层配合：ChapterPlanner 确定性切章节 → Map-Reduce 分段处理 → ChapterCache 让重跑几乎免费。三者缺一不可。"

### Q6：如果重新做，你会改什么？

> "一是把 Critic 和 Reviser 的 prompt 模板外置成配置文件，方便非开发人员调优。二是给 Map-Reduce 的 reduce-global 也加缓存——目前每次重跑都要 30 秒，虽然不大但可以更极致。"

## 结尾（30 秒）

> "总结一下，LectureMind 是一个从视频到可问答讲义的端到端系统。技术上覆盖了多模态采集、VLM 分级、LLM Agent 协作、Map-Reduce 分段处理、双投影编译、混合检索 RAG 这些领域。工程上我在缓存策略、失败隔离、可观测性方面做了比较多的思考。代码开源，欢迎交流。"
