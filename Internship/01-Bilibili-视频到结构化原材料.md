# Bilibili 视频到结构化原材料

## 文档目的

这份文档聚焦 LectureMind 的输入侧链路，即系统如何把一个 Bilibili 视频链接转换为后续可处理的结构化原材料。它主要服务三个用途：

- 项目复盘时，快速回忆输入侧有哪些模块、边界和降级策略。
- 写简历时，提炼“我做的不只是调接口，而是搭了一条采集与预处理链路”。
- 面试时，回答“你的系统输入是什么、稳定性怎么保证、失败怎么处理”。

## 一句话定义

LectureMind 的第一段主链路，不是直接把视频 URL 丢给大模型，而是先把视频变成一组可复用、可缓存、可追踪的原材料，包括视频元数据、字幕、关键帧和封面，再交给后续理解与编排模块。

## 这一段链路解决了什么问题

如果把视频总结理解成一次性 prompt 调用，会遇到几个现实问题：

- 长视频上下文过大，原始材料本身就需要先拆解。
- 视频内容不只是字幕，图示、公式、代码截图同样重要。
- 同一个视频可能会被重复处理，缺少本地缓存会导致成本高、调试困难。
- 输入源并不稳定，字幕缺失、Bilibili 抓取异常、关键帧提取失败都需要降级处理。

这个项目的做法是先把“视频”分解成后续模块真正需要消费的原材料，再进入理解层。

## 代码层面的模块边界

从目录结构和主链路调用看，输入层的核心模块有：

- `app/ingest/bilibili.py`
  负责解析 Bilibili 链接或 BV 号，并抓取视频元数据。
- `app/ingest/subtitle.py`
  负责提取字幕；在无可用字幕时，走 Whisper 回退路径。
- `app/ingest/keyframe.py`
  负责抽取关键帧，作为视觉理解的基础输入。
- `app/ingest/cover.py`
  负责封面抓取与缓存。
- `app/ingest/cookies.py`
  负责处理 Bilibili 抓取可能需要的 cookie。
- `app/pipeline.py`
  在主流程中统一编排这些输入模块。

其中最关键的事实证据来自 `app/pipeline.py`。该文件把输入侧分成两个阶段：

- 先单独获取元数据。
- 再并行执行字幕提取、关键帧提取和封面抓取。

这说明系统并不是顺序串行地“一个一个做完”，而是明确做了可以并行的输入预处理编排。

## 主处理流程

输入侧链路可以概括为：

1. 用户提交 Bilibili 链接或 BV 号。
2. 系统先解析 BV，并获取标题、作者、时长、封面地址等元数据。
3. 系统并行拉起三个任务：
   - 提取字幕；
   - 抽取关键帧；
   - 下载封面。
4. 输入资产被持久化到本地数据目录和 SQLite 中。
5. 后续理解模块消费这些原材料，而不是重新直接访问视频页面。

从 `app/pipeline.py` 看，这里至少有两个设计值得强调：

- **并行采集。** 字幕、关键帧、封面只依赖元数据，因此能并行执行。
- **采集结果持久化。** 字幕与关键帧结果会写入数据库和本地 `data/` 目录，便于后续复用与调试。

## 数据落点与可复用性

根据 `README.md`、`docs/deploy.md` 和 `app/storage/db.py`，输入侧的关键数据通常会落到：

- `data/subtitles/`
- `data/keyframes/`
- `data/audio/`
- `data/debug/`
- `data/app.db`

数据库中还会记录：

- `assets` 表：记录字幕、关键帧等资产路径与元信息。
- `jobs` 表：记录任务状态、进度与错误信息。

这意味着输入层不是临时脚本式处理，而是一个具备本地知识仓和任务跟踪能力的采集层。

## 关键工程化设计

### 1. 缓存优先，而不是每次重跑

在 `app/pipeline.py` 中，系统会先检查已有总结记录和报告文件。如果已存在且状态完成，会直接返回缓存结果，而不是重复采集和生成。

这对项目有两个价值：

- 降低大模型与视频处理成本。
- 让调试、重渲染和 UI 迭代可以建立在已有数据之上。

### 2. 并行化输入准备

字幕、关键帧和封面的处理通过 `asyncio.gather` 并行执行，这是一个典型的 I/O 密集型优化点。  
对简历和面试来说，这比“我做了一个调用外部 API 的工具”更像一个完整工程系统。

### 3. 降级与容错

根据 `README.md` 和 `docs/deploy.md`，系统明确考虑了这些场景：

- 公开抓取不稳定或 `403` 时，支持 cookie 文件。
- 字幕缺失时可回退到 Whisper。
- 某些视觉能力不可用时，不会阻断整条主流程。

这类设计很适合在面试中说明你对真实输入环境的理解，而不是只考虑 Happy Path。

## 和后续模块的接口关系

输入层的输出，不是最终讲义，也不是 Copilot 结果，而是后续理解层的上下文：

- 视频基础信息；
- 字幕分段；
- 关键帧列表；
- 封面；
- 已缓存的输入资产路径。

这些数据在 `app/pipeline.py` 中被组装为后续 `LecturizeContext` 的输入。这说明输入层和理解层之间存在相对清晰的职责边界。

## 适合写进简历的亮点

- 搭建了 Bilibili 视频采集与预处理链路，支持元数据抓取、字幕提取、关键帧抽取与封面缓存。
- 将字幕、关键帧、封面并行处理，并把中间资产落地到本地数据目录与 SQLite，支持缓存复用和任务追踪。
- 为字幕缺失、抓取受限等场景设计了 Whisper 和 cookie 等降级方案，提升处理稳定性。

## 适合面试展开的问题

### 1. 为什么不直接把整段视频或字幕丢给大模型

可以从三个角度回答：

- 输入过大，必须先做结构化拆解。
- 学习型讲义不只依赖字幕，还依赖视觉证据。
- 需要可复用、可缓存、可调试的输入资产。

### 2. 为什么要抽关键帧

因为很多技术视频的核心信息并不在字幕，而在 PPT、白板、公式、代码截图或界面变化上。关键帧为视觉理解和证据锚点提供基础材料。

### 3. 为什么要把数据落到本地

因为这能支持：

- 失败重试；
- 报告重渲染；
- Copilot 和 MCP 的后续消费；
- 低成本重复查询和调试。

## 当前文档中的事实与推断

### 事实

- 项目支持 Bilibili 链接或 BV 号输入。
- 输入侧包括元数据、字幕、关键帧、封面处理模块。
- `app/pipeline.py` 中对字幕、关键帧、封面做了并行采集。
- 输入结果会持久化到 `data/` 和 SQLite。
- 系统具备缓存命中、cookie、Whisper 等回退机制。

### 推断

- 这一层的目标不仅是抓数据，更是为后续理解层建立稳定、可复用的原材料接口。

这个推断与代码结构和 README 表述一致，但本质上仍是架构归纳，不应和“代码里直接写明的注释”混为一谈。
