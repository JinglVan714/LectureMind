# 结构化讲义生成与双投影建模

## 文档目的

这份文档聚焦 LectureMind 的中枢能力：如何把字幕、关键帧等原材料转换成可阅读讲义，并进一步拆成“面向读者的讲义结构”和“面向系统的证据结构”两套投影。  
这是整个项目最值得用于简历和面试深挖的部分。

## 一句话定义

LectureMind 不是直接生成一份视频摘要，而是先构建 `LectureIR`，再把它编译成讲义与证据两套结构，从而同时满足“可阅读”和“可检索、可追溯”两种目标。

## 这部分为什么是项目核心

普通视频总结产品往往只有一个终点：生成一段文字。  
而这个项目的目标更像是构建一个学习型知识表面，因此中间层必须回答两个问题：

- 如何把原始视频材料组织成读者可顺着读下去的讲义。
- 如何保留足够的证据锚点，让后续系统还能回到章节、时间点、关键帧和引用。

也正因此，项目没有把 HTML 当成唯一产物，而是把结构化中间表示放在更前面的位置。

## 代码中的核心模块

这部分能力主要分布在：

- `app/understand/ir.py`
- `app/understand/ir_builder.py`
- `app/understand/lecture_compiler.py`
- `app/understand/evidence_index.py`
- `app/understand/lecture_blueprint.py`
- `app/understand/composition.py`
- `app/understand/chapter_planner.py`
- `app/understand/length_adapt.py`
- `app/understand/profile.py`

从主链路 `app/pipeline.py` 看，系统在完成输入准备和关键帧描述后，会构造 `LecturizeContext`，再进入 `LectureIR` 构建、章节规划、长度路由、编译和渲染。

## 核心中间表示：LectureIR

`app/understand/ir.py` 定义了这个项目最重要的数据结构之一：`LectureIR`。

它并不是一份简单的“总结文本”，而是一种结构化讲义中间表示，至少包含这些维度：

- 视频基础信息：`bv_id`、标题、作者、时长、封面。
- 讲义画像：`LectureProfile`，包括视频主类型、密度、必选章节等。
- 主问题与主线：`core_question`、`mainline`。
- 章节结构：每章的标题、时间范围、摘要、学习目标、教学笔记、步骤、要点、关键帧、陷阱、总结。
- 知识单元：`knowledge_units`。
- 视觉证据：`visual_evidence`。
- 完整性评估：`completeness`。
- 渲染计划：`render_plan`。
- 复习题与学习问题：`review_questions`、`study_questions`。

这个设计的意义在于：  
系统不是把大模型输出当成“最终可直接展示的文本”，而是先约束成一份可继续加工、校验、投影的结构化表示。

## 长视频处理：不是一套 prompt 打天下

`app/pipeline.py` 和 `app/config.py` 能看出一个很重要的设计：  
系统会根据视频长度选择不同的生成路径，而不是所有视频都走同一套处理逻辑。

这里至少有三层机制：

- `profile`：根据时长划分视频档位。
- `chapter planner`：先推断章节锚点。
- `length-aware routing`：决定是否启用 map-reduce、chapter cache、critic、reviser 等后续能力。

从 `app/config.py` 的注释还能看出，这些阈值不是拍脑袋定的，而是和真实视频长度、输出 token 上限有关。  
这对面试非常加分，因为它体现出你不是只写了功能，而是处理了长上下文的现实约束。

## 从 LectureIR 到“双投影”

`app/understand/lecture_compiler.py` 体现了这个项目和普通总结器最不一样的地方。  
它并不是把 `LectureIR` 直接渲染成 HTML 就结束，而是做了至少四件事：

1. 把 `LectureIR` 规范化。
2. 构建 `LectureBlueprint`。
3. 构建 `LectureNoteIR`。
4. 构建 `EvidenceIndex`。

也就是说，`LectureIR` 会继续被投影成两套互补结构：

- **Lecture Note IR**
  面向读者，强调教学单元、阅读顺序、核心信息和内容块组织。
- **Evidence Index**
  面向系统，强调证据对象、关系、时间锚点、页面锚点、RAG chunk 和可追溯路径。

这是整个项目的架构亮点之一。

## 面向读者的投影：Lecture Note IR

从 `app/understand/lecture_compiler.py` 可见，`note_composition()` 会把章节组织为一组 `TeachingUnit`，每个单元包含：

- 标题与序号；
- 教学目标；
- 单元角色；
- 核心信息；
- 内容块；
- 视觉槽位；
- 证据引用；
- 对应的原始章节引用。

内容块还会按类型进一步组织，例如：

- `claim`
- `process`
- `boundary`
- `synthesis`

这说明项目并不是简单按章节拼接，而是在尝试把视频讲解重组为更符合阅读和复习习惯的讲义结构。

## 面向系统的投影：Evidence Index

`app/understand/evidence_index.py` 则把讲义映射成另一套结构，核心包括：

- `evidence_objects`
- `evidence_relations`
- `anchor_map`
- `projection_views`

它会为不同内容构造不同类型的证据对象，例如：

- `chapter_evidence`
- `quote_evidence`
- `frame_evidence`
- `procedure_evidence`
- `concept_evidence`

并把这些对象关联到：

- 视频时间锚点；
- 页面锚点；
- 讲义节点；
- RAG chunks；
- 证据之间的支持关系。

换句话说，Evidence Index 的作用不是给读者看，而是让系统知道“这一段回答、这一张关键帧、这一条讲义块，具体能回溯到哪里”。

## 为什么要做双投影

这是面试里非常适合单独展开的问题。

如果只保留一套结构，会出现冲突：

- 面向读者的最佳组织方式，往往强调阅读顺序、解释性和教学性。
- 面向系统的最佳组织方式，往往强调细粒度对象、可检索性和锚点关系。

把两者强行塞进同一个结构，通常会导致：

- 页面结构不自然；
- 检索对象过粗或过碎；
- 后续 Copilot 很难稳定回到具体证据。

因此，项目把“可读”和“可检索”拆开建模，这是一种很典型、也很成熟的系统设计取舍。

## 编译阶段的价值

从 `app/understand/lecture_compiler.py` 和相关测试 `tests/test_lecture_compiler.py` 看，这个阶段不只是格式转换，还承担了几个职责：

- 对内容类型做判别，例如更偏概念讲解还是流程讲解。
- 按内容类型选择不同块组织策略。
- 去重、合并、补充边界信息。
- 把内容映射为向后兼容的 `composition` 输出。

这说明“讲义生成”不是一次大模型生成的末端，而是一个真正存在编译逻辑的中间层。

## 适合写进简历的亮点

- 设计并实现了视频讲义的中间表示 `LectureIR`，将原始字幕、关键帧和讲解内容结构化为章节、知识单元、视觉证据与复习问题。
- 设计“讲义视图”和“证据视图”双投影架构：前者面向阅读与复习，后者面向检索、锚点回溯和下游 Agent 消费。
- 针对长视频设计了基于时长档位的路由与章节规划机制，避免单次大模型调用在上下文和输出长度上失控。

## 适合面试展开的问题

### 1. 为什么要先做 IR，而不是直接生成 HTML

因为 HTML 是最终展示层，不适合作为事实源。  
中间表示更适合做：

- 校验；
- 编译；
- 重渲染；
- 检索；
- 多消费端复用。

### 2. 为什么要把讲义和证据拆成两套结构

因为读者关注的是“怎么读懂”，系统关注的是“怎么检索与回溯”。  
这是两个目标，不能指望一种结构天然兼顾。

### 3. 你怎么处理长视频

可以从三个角度回答：

- 先按时长做 profile 路由；
- 再用 chapter planner 做分段；
- 必要时走 map-reduce、cache 和 critic / reviser 等路径。

### 4. 这一段和普通“视频总结”最大的区别是什么

最大的区别不是多用了几个模型，而是：

- 有结构化 IR；
- 有双投影；
- 有证据锚点；
- 后续还能服务于 Copilot 和 MCP。

## 当前文档中的事实与推断

### 事实

- 项目定义了 `LectureIR` 结构。
- `app/pipeline.py` 中存在长度路由、章节规划和 IR 构建流程。
- `app/understand/lecture_compiler.py` 会产出 `LectureBlueprint`、`LectureNoteIR`、`EvidenceIndex` 和 `composition`。
- `app/understand/evidence_index.py` 会构造多种 evidence object 与 relation。
- `tests/test_lecture_compiler.py` 对编译结构做了直接验证。

### 推断

- 该项目的核心竞争力在于把“视频总结”升级为“学习型讲义编译系统”。

这个判断来自代码结构、README 定位和编译链路，但它仍属于总结性归纳。
